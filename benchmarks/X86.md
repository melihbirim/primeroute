# Native x86 optimization

This experiment compares the preserved portable implementation with the new
x86 path, C++ primesieve 12.18 and Rust primal 0.3.3. All timed implementations
use one thread. The original M2 reports and their hashes remain unchanged.

## Implementation

The default Rust build remains portable. Runtime detection selects AVX2 bitmap
population counts, eight-lane stream rotation and vector decoding into both
`usize` prime lists and `u32` seed lists. POPCNT counting and POPCNT/BMI1 decoding
provide intermediate fallbacks; the original portable decoding remains available.

Long x86 requests process primes through 32,768 in 32 KiB cache chunks. Larger
dense primes advance once per full window, avoiding four state visits for only
a few marks. Dense primes share a constant-mask loop by residue class. Medium primes share constant wheel
steps by current state; their queues retain compact eight-byte entries and reuse
allocations between windows. Prime activation still starts at the appropriate
square. The ARM marking, NEON and router implementations retain their existing
algorithms. No query answers are cached.

Requests below eight bitmap windows keep flat marking. The hybrid pilot improved
long counting but regressed scattered and mixed batches by 15.7% and 11.3% on
its VM. Short multi-window calls now mark the original state arrays directly.
Batch seed tables through 2²⁰ copy the already embedded metadata prefix instead
of sieving it again. Larger seed tables are still generated for the call. This
bounded metadata was present in the baseline; no query-answer cache was added.

## Native x86 results

Measured on 25 November 2026, on an **AMD EPYC 9V74 VM**, pinned to logical CPU
0. AVX2 was available; AVX512 BW/VBMI2 were unavailable to this VM. Every timed
implementation uses one thread. Times below are milliseconds.

| Count through | Baseline | Candidate | primesieve | primal |
| --- | ---: | ---: | ---: | ---: |
| 100 million | 15.273 | 10.030 | 8.940 | 12.970 |
| 1 billion | 150.495 | 105.406 | 107.397 | 169.342 |
| 10 billion | 1766.127 | 1374.820 | 1146.608 | 2256.006 |
| 100 billion | 22882.613 | 17667.620 | 13886.848 | 31934.439 |

Counting takes **22–34% less time than the baseline**, including **22.8% less
at 100 billion**. All twelve range cases improve: counting by 20–43% and listing
by 33–46%. The scattered 10¹² batch improves from 6.042 to 5.780 ms; mixed
queries improve from 8.654 to 8.138 ms. These remove the regressions seen in
the earlier candidates.

The candidate improves **21/26 cases versus the baseline**, with five ties and
no losses under the 3% comparison band. Against primesieve it has **6 wins,
1 tie and 19 losses**. The one-billion count is a tie; primesieve still leads
the other prefix counts and all tested ranges. Against primal the candidate
wins **25/26**; primal remains faster on the scattered 10¹² batch.

The baseline v3 control takes 131.387 ms at one billion, versus 150.495 ms for
the portable baseline. Build flags help, but the new default build is faster
again at 105.406 ms. The improvements require no CPU flag from the caller.

The [full paired tables](experiments/x86-2026-11-25/paired-summary.md) include
every prefix, range and batch case, both v3 controls and every remaining loss.
The [raw Linux report](experiments/x86-2026-11-25/inplace-paired/x86-diagnostic-4daa4743e66531c6f50129d6b0fe4c8834bf98c7/paired-results.json)
contains all samples and commands. Scores use full-precision medians; rounded
table values do not decide wins or ties.

## Measurement method

The Linux comparison runs natively on a GitHub Actions x86 VM. Baseline,
candidate and competitors run on that same VM, sequentially, with inherited
affinity to one logical CPU. Command order rotates and reverses between rounds.
The local M2 comparison uses the same driver without affinity. Compilation is
outside timing. Neither cross-compilation nor emulation supplies timing results.

The candidate uses the default Rust target with runtime feature detection. A
separate baseline and primal build use `-C target-cpu=x86-64-v3` as controls on
Linux. C++ uses its normal Release build and runtime cache detection. Prefix and
range comparisons also try an explicit 1024 KiB C++ sieve; comparisons use the
faster median where both settings are measured. At 100 billion, C++ default and
default-target primal are measured; no v3 or alternate-cache control is included
in that long case.

The paired suite has **26 cases**: four prefix counts, twelve inclusive
count/list ranges and ten batches. Linux uses nine samples after two warm-ups
for the smaller prefixes and ranges. M2 uses fifteen after three. At 100 billion,
Linux uses three samples and M2 five, both after one warm-up. Batches use five
samples after one warm-up on both machines. Ranges include three fresh requests
per sample and an additional untimed validation request inside each helper.

Prefix times include process startup and output capture. Range times are inside
the process and include setup, allocation, computation, list checksums and
destruction. Batch times include sorting, routing, computation and restoration of
input order, excluding process startup, parsing and serialization. Each batch
sample is the first library call in a fresh process. Primal ranges
use the documented segmented adapter, since primal has no public range-sieve API.

Every invocation must produce the expected prime count, range count/checksum or
complete next-prime answer array. Saved expected values are validation data only.
All timed implementations compute their results. The driver hashes sources and
executables before and after timing and publishes a completed report only if
they match. Raw reports retain every sample and command, CPU information,
compiler versions, affinity and source/binary hashes.

## Validation

Native Linux passes 36 correctness tests in debug and release, including both
x86 decoders across all 65,536 two-byte masks, padded output near the `u32`
endpoint, vector-counter tails, grouped state transitions and prime-square
activation across windows. Four ignored profiles run separately to choose
kernels; their loop timings are not reported as full-query performance.
ARM passes all 29 correctness tests in both profiles. Seed-prefix checks include
zero, 2²⁰ and the first bound above that table. Formatting and Clippy pass
for the library and benchmark crate on both platforms. Python summary regression
tests and actionlint also pass.

## Reproduce

The [experiment workflow](../.github/workflows/x86-optimization.yml) builds the
preserved baseline, a v3 control, the candidate and C++ on a fresh native x86 VM.
It then invokes [platform_compare.py](platform_compare.py). Its benchmark branch
trigger keeps these longer experiments separate from normal push/PR checks.

For a local comparison, build the library, example and benchmark helpers in both
the preserved baseline and current tree. Compile `range_bench.cpp` and
`batch_next.cpp` against a Release static primesieve build, then run:

```sh
python3 benchmarks/platform_compare.py \
  --baseline benchmarks/experiments/x86-2026-11-25/baseline \
  --primesieve-dir /path/to/primesieve \
  --cpp-range /path/to/range-bench-cpp \
  --cpp-batch /path/to/batch-next-cpp \
  --output /path/to/new-results.json --large
```

Use a new output path. Keep sources and executables frozen until the run ends.
The archived baseline is a source snapshot, not a dependency of the library.
